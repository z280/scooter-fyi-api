# Multi-provider, multi-city — API plan

Status: **proposal**, nothing here is built. Companion doc:
`denver-scooter-fyi/docs/MULTI_CITY_FRONTEND_PLAN.md`.

This is an assessment of what it would actually take to run this API for
more than Denver and more than Veo, written against the code as it stands
at `main` (sql/054, ~26k lines of Python).

---

## 1. Three axes, currently conflated

Almost every "Denver" in this repo is really one of three different things,
and they need separating before anything else:

| Axis | What varies | Where it lives today |
|---|---|---|
| **City** | boundaries, envelope, timezone, tax rate, routing graph, geocoder index, compliance rules | `config.json` (mostly), `data/*.geojson`, `ZoneInfo("America/Denver")` in 5 modules, `_denver` column suffixes |
| **Provider** | feed shape, stable-id derivation, vehicle registry, battery semantics, pricing, deep links, QR format | `src/ingest.py`, `src/identity.py`, `src/quality.py`, `src/battery_model.py` |
| **Deployment** | domain, CORS, magic-link URL, branding | `config.json`, frontend |

The good news is that the city axis is already ~85% config-driven — the
v3.3 generalization did most of that work. The provider axis is the one
with real semantics behind it, and it is the one to attack first (§7).

### 1a. The city coupling that is *not* config

Everything else is already a `config.json` key. These are not:

- **`_denver` metric suffixes** — `total_devices_denver`, `percent_bikes_denver`,
  `total_not_in_denver`, generated by `equity_groups.core_metric_columns()` and
  materialized as real columns in `snapshot_metadata_core` and
  `daily_sla_compliance`.
- **`spatial_status = 'denver_core'`** — a `CHECK` constraint in `sql/001_init.sql`,
  read by `compute.py`, `device_state.py`, `api_public.py`, `api_h3.py`.
- **`ZoneInfo("America/Denver")`** — hardcoded in `quality.py`, `daily_sla.py`,
  `daily_trips.py`, `dwell_stats.py`, `weather.py`. Every daily rollup boundary
  and the 8am–8pm "daylight dwell" rule depend on it.
- **`equity_groups.TRACKED_GROUPS`** — `v1, v2, er1..er6` is Denver DOTI's
  Equity Index. No other city has this taxonomy; most will have none at all.
- **`data/*.geojson`** — 11 boundary files baked into the image.
- **Denver's RFP §3.0 compliance model** — the 30% SLA, `daily_sla_compliance`,
  `compliance_<g>_pass`. This is a *contract with one city*, not a feature.

### 1b. The provider coupling

- **`ingest._NUMBER_RE`** — pulls the plate out of `rental_uris.…?&number=`.
  That is a Veo convention, not GBFS.
- **`ingest._KNOWN_VEHICLE_TYPES`** — hand-verified ground truth correcting
  Veo's own `vehicle_types.json` (id=4 and id=5 are mislabeled upstream).
  Every provider will need its own version of this, and it can only be built
  by looking at vehicles in the field.
- **`identity.hash_plate`** — `HMAC(salt, plate)[:16]`. **No provider namespace.**
  See §5, this is the one genuine correctness bug waiting to happen.
- **`quality.py`** — the battery-percent recovery is a reverse-engineered SoC
  curve for Veo hardware; the `great/good/acceptable/poor` cutoffs are
  expressed against it.
- **`battery_model.py`** — an empirical regression fit on Veo vehicles,
  trainable only after ~2 weeks of observations *per vehicle model*.

## 2. Should `v1` become the city name?

**Recommendation: no.** Three reasons:

1. `/api/v1/` is a *contract* version. Spending it on tenancy means the API
   can never be versioned again without a second dimension anyway.
2. **Most endpoints aren't city-scoped.** Accounts, sessions, profile,
   points ledger, emoji-nouns/adjectives/royalty-titles, `photos/mine`,
   `meta/privacy`, all of `auth/*` — a rider is one person regardless of
   which city they're standing in. `/denver/profile` and `/boulder/profile`
   returning the same row is a design smell that will leak into the client.
3. It is a hard break for every existing consumer on day one, including the
   live frontend and API.md's 3,194 lines of documented shapes.

**Instead:** scope only the resources that are actually city-scoped, and do
it in two compatible steps.

**Step A — query parameter, default `denver`.** Zero-break:

```
GET /api/v1/devices/current?city=denver&provider=veo
GET /api/v1/devices/current                 # identical to the above
```

`city` and `provider` resolve through one FastAPI dependency
(`Depends(resolve_scope)`) that returns a `Scope(city, provider|None, feed_ids)`.
Unknown city → `404 unknown_city`. Omitted → the configured default. Today's
frontend keeps working byte-for-byte, which means Phase 1 can ship to prod
before any client work exists.

**Step B — path alias for the city-scoped set.** Once step A is proven:

```
GET /api/v1/c/{city}/devices/current
```

This costs a refactor: the routers currently hardcode `/api/v1/…` in each
decorator, so mounting them under a prefix means rewriting every path to be
router-relative and mounting each router twice (bare + prefixed). Mechanical,
but it touches ~25 files. Worth doing only if you want the city in the URL
for caching/CDN reasons — `?city=` is already a perfectly good cache key.

The endpoints that stay **unscoped**: `auth/*`, `profile/*`, `points`,
`lexicon`, `photos/mine`, `meta/privacy`, `rides/*` (off-feed rides are
about a vehicle we don't track anywhere), `legal/*`.

The endpoints that become **scoped**: `snapshots/*`, `spatial-snapshot`,
`analytics/trend`, `boundaries*`, `devices/current`, `equity-estimate`,
`h3/aggregates`, `compliance/*`, `route*`, `geocode/search`,
`reports/summary`, `reports/export`, `leaderboard/map`, `meta/pricing`,
`user/devices/current`, and all of `private/*`.

## 3. The `feed` abstraction

The unit of ingest is not a city and not a provider — it is the pair. Model
it explicitly:

```sql
CREATE TABLE cities (
    city_id      SMALLSERIAL PRIMARY KEY,
    slug         TEXT UNIQUE NOT NULL,        -- 'denver'
    display_name TEXT NOT NULL,               -- 'Denver'
    timezone     TEXT NOT NULL,               -- 'America/Denver'
    bbox_west    NUMERIC(9,6) NOT NULL, ...   -- replaces envelope.denver_core
    center_lat   NUMERIC(9,6) NOT NULL, ...
    tax_rate     NUMERIC(6,5),                -- replaces pricing.tax_rate
    currency     TEXT NOT NULL DEFAULT 'USD',
    status       TEXT NOT NULL DEFAULT 'live' -- live | beta | hidden
);

CREATE TABLE providers (
    provider_id  SMALLSERIAL PRIMARY KEY,
    slug         TEXT UNIQUE NOT NULL,        -- 'veo'
    display_name TEXT NOT NULL,
    adapter      TEXT NOT NULL,               -- 'veo' | 'gbfs' | …  (see §7)
    capabilities JSONB NOT NULL DEFAULT '{}'  -- see §7a
);

CREATE TABLE feeds (
    feed_id        SMALLSERIAL PRIMARY KEY,
    city_id        SMALLINT NOT NULL REFERENCES cities(city_id),
    provider_id    SMALLINT NOT NULL REFERENCES providers(provider_id),
    gbfs_url       TEXT NOT NULL,
    vehicle_types_url TEXT,
    cycle_minutes  SMALLINT NOT NULL DEFAULT 2,
    enabled        BOOLEAN NOT NULL DEFAULT TRUE,
    UNIQUE (city_id, provider_id)
);
```

Denver+Veo is `feed_id = 1`, seeded from today's `config.json`. Everything
in `config.json`'s `gbfs`, `envelope`, `pricing` blocks moves here; the
`boundaries` list gains a `city` key; `valhalla`/`geocode`/`cors`/`auth`
stay global.

Why a table and not more `config.json`: feeds need per-feed *state*
(`last_updated`, last cycle, enable/disable without a deploy) and are
referenced by FK from the pipeline tables. `config.json` remains the right
home for things with no rows pointing at them.

## 4. Schema: adding the tenant column

This is the single largest chunk of work — roughly 30 of the 45 tables.

**Gets `feed_id`** (ingest-derived, one provider's view of one city):
`observation_cycles`, `api_failures`, `raw_telemetry_points`,
`snapshot_metadata_core`, `regional_metrics_narrow`, `daily_sla_compliance`,
`device_state`, `device_history`, `trip_events`, `daily_trip_summary`,
`daily_vehicle_trip_counts`, `battery_trip_observations`,
`battery_model_coefficients`, `device_qr_codes`, `hourly_temperature`
(really city, not feed — see below).

**Gets `city_id`** (geographic, provider-independent): `hourly_temperature`,
`h3_r8_area_report`, `h3_r8_area_leaders`, `h3_r8_area_leader_runs`,
`regional_leaders`.

**Gets both, or inherits via `vehicle_identifier`**: `negative_reports`,
`quality_feedback`, `device_reports`, `discount_reports`, `model_reports`,
`device_recommendations`, `device_photos`, `tracked_rides`,
`user_device_watch_list`, `ride_waypoints`, `track_donations`,
`donated_track_points`, `ride_routes`, `ride_surveys`. Prefer a denormalized
`feed_id` on these rather than a join — the reporting queries all filter on it.

**Stays global**: `accounts`, `auth_sessions`, `magic_link_tokens`,
`login_codes`, `sms_login_codes`, `rate_limit_events`, `admin_allowlist`,
`user_points`, `user_preferences`, `sfw_adjectives`, `emoji_nouns`,
`royalty_titles`, `ruling_colors`, `comms_replies`, `rides` (off-feed),
`off_feed_ride_waypoints`, `system_state` (or key it by feed in the key
string), `schema_migrations`.

**Backfill is trivial** — there is exactly one tenant today, so every
migration is `ADD COLUMN … ; UPDATE … SET feed_id = 1 WHERE feed_id IS NULL;
ALTER … SET NOT NULL;`. Do it in that order, in separate statements, so the
`_pg.py` replay-over-live-data test in `test_migration_replay_pg.py` still
passes.

### 4a. Indexes and constraints that need re-thinking, not just a column

- Every index in the "slider lookup" family (`idx_metrics_slider_lookup`,
  `idx_raw_snapshot_time`, …) needs `feed_id` as the **leading** column, or
  Denver's volume will dominate every other city's query plan.
- `device_state.vehicle_identifier` is the **primary key**. Becomes
  `(feed_id, vehicle_identifier)` — or see §5.
- `device_qr_codes.vehicle_identifier` — same.
- `idx_rides_one_active_per_account` (partial unique on `status='active'`):
  keep it **global**, not per-city. A rider is in one place at a time; a
  per-city version would let someone hold three active rides in three cities.
  Same for `tracked_rides`' one-active constraint. This is a product decision,
  make it deliberately.
- `regional_metrics_narrow` PK `(cycle_id, region_type, region_name)` is
  already safe, since `cycle_id` will be feed-scoped.
- `snapshot_metadata_core` PK is `cycle_id` — also already safe.

### 4b. `spatial_status`

`CHECK (spatial_status IN ('denver_core','china_glitch','other_outlier'))`.
Rename the value to something city-neutral — `service_area` — in one
migration that drops the constraint, `UPDATE`s the rows, and re-adds it.
`china_glitch` is a Veo-feed artifact; generalize to `geo_glitch` and make
the box a per-provider config entry rather than a global one. Keep an
`other_outlier` catch-all.

Grep targets for the rename: `compute.py` (34 Denver refs, most of them
this), `device_state.py`, `api_public.py`, `api_h3.py`, `api_private.py`,
`archive.py`.

### 4c. The 22 core metrics

`snapshot_metadata_core` is a wide table whose column names are generated
from `equity_groups.core_metric_columns()`. With Denver's 8 groups × 2 split
dimensions it is already ~100 columns. Multiplying that by cities is not an
option.

Two viable paths:

- **Cheap:** rename the `_denver` suffix to `_citywide`, make `TRACKED_GROUPS`
  come from the city row instead of a module constant, and accept that the
  table's column set is the *union* of every city's groups (other cities
  write NULL into Denver's `er*` columns). Works fine up to a handful of
  cities that mostly have no equity taxonomy at all.
- **Right:** move to a narrow table
  `(feed_id, snapshot_time, group, dimension, value, total, percent)` and
  keep a Denver-shaped view over it for API compatibility. More work, but
  it also kills the "add a group = add 20 columns via a migration" ritual
  that `equity_groups.py`'s docstring currently has to warn about.

I'd take the cheap path in Phase 1 and the right one only if city #3 also
turns out to have a compliance regime.

### 4d. Retention arithmetic

`raw_telemetry_points` at 2-minute cadence for one Denver-sized fleet is
already ~12.5M rows per 48h — which is why `archive_hours` was cut to 24.
Fifteen feeds at the same cadence is ~90M rows/day. Before city #2:

- make `cycle_minutes` per-feed (already in the `feeds` table above) and
  default new feeds to 5 or 10 min,
- partition `raw_telemetry_points` by `feed_id` (or by day) so the archive
  `TRUNCATE` becomes a `DROP PARTITION`,
- confirm the archive job's DuckDB→Parquet burst still fits the scheduler's
  1 GiB cap when it is exporting N feeds. It almost certainly does not; make
  it archive one feed per invocation.

## 5. `vehicle_identifier` needs a provider namespace

`hash_plate()` is `HMAC-SHA256(salt, plate)[:16]` — 64 bits, no namespace.
Veo plates are ~7-digit numbers. If Lime's stable id is also numeric, the
two live in the same 64-bit space and nothing prevents a collision from
silently merging two vehicles' history, reports, photos and rides. The
docstring's collision math ("≈2e-12 at 8k devices") assumed one fleet.

Do **not** re-derive existing identifiers — they are stored in ~16 tables
and printed in QR flows. Instead:

1. Add `feed_id` (or `provider_id`) to `device_state`, `device_history`,
   `device_qr_codes` and make the key composite. Lookups become
   `(feed, identifier)`.
2. For **new** providers only, derive as `hash_plate(f"{provider_slug}:{plate}")`
   so cross-provider collisions are impossible by construction. Veo keeps
   its bare-plate derivation. Encode that in `identity.py` as an explicit
   per-provider rule with a comment saying why Veo is the exception, or
   nobody will believe it later.
3. `api_qr.py`'s payload validation and `ride-deeplink.ts`'s
   `^[0-9a-fA-F]{16}$` stay valid — the format doesn't change, only the
   namespace it's minted in.

Also worth deciding now: several providers rotate their GBFS `vehicle_id`
per trip *and* publish no plate. For those there is **no stable identifier
at all** (§7b).

## 6. Time, weather, and the daily rollups

`ZoneInfo("America/Denver")` is load-bearing in five places:

- `daily_sla.py` — the 6–9am compliance window
- `daily_trips.py` — the calendar-day rollup boundary
- `quality.py` — the 8am–8pm "daylight dwell" demerit
- `dwell_stats.py`
- `weather.py` — `hourly_temperature` is a Denver-wide series

All become `ZoneInfo(city.timezone)`, resolved from the feed. The subtlety:
`crontab` runs the scheduler container at `TZ=America/Denver`, so
`0 9 * * *` means 9am Denver. With multiple timezones, the cron entry must
fire more often than the work needs and each job selects the cities whose
local time has just crossed the boundary — i.e. run `daily_sla` hourly and
have it no-op for cities where it isn't 9am yet. Idempotency is already
there (`ON CONFLICT`), so this is safe.

`weather.py` needs one temperature series per city, keyed by `city_id`,
because the battery model regresses on it.

## 7. Provider adapters

Your instinct — a Lime path and a Bird path separate from Veo — is right
about the *outcome* but I'd build it as **one pipeline with pluggable
front-ends**, not three pipelines. Everything downstream of normalization
(envelope tagging, H3 indexing, the DuckDB spatial join, `device_state`,
`ride_watch`, `trip_events`, ranking, archive) is provider-agnostic already
and should stay that way.

```python
# src/providers/base.py
class ProviderAdapter(Protocol):
    slug: str
    capabilities: Capabilities

    def fetch(self, feed: Feed) -> RawFeed: ...
        # HTTP, auth, pagination, per-provider error mapping → UpstreamError

    def normalize(self, raw: RawFeed) -> list[NormalizedDevice]: ...
        # → today's TaggedDevice minus the spatial tagging

    def stable_id(self, entry: dict) -> str | None: ...
        # Veo: rental_uris &number=  |  generic GBFS: None

    def vehicle_registry(self) -> dict[str, KnownVehicleType]: ...
        # Veo: today's _KNOWN_VEHICLE_TYPES  |  generic: {} (trust upstream)

    def battery_percent(self, d: NormalizedDevice) -> float | None: ...
        # Veo: the SoC LUT  |  generic: current_range / max_range_for_type
```

- `VeoAdapter` — today's `ingest.py`, moved verbatim. No behavior change.
- `GbfsAdapter` — a spec-compliant baseline (GBFS 2.3 + 3.0
  `free_bike_status`/`vehicle_status`). Lime and Bird both publish GBFS, so
  this is probably *both* of them plus a capability declaration and a
  vehicle registry. Only fork into `LimeAdapter`/`BirdAdapter` when you find
  a concrete divergence — and record what the divergence was in the class
  docstring, the way `_KNOWN_VEHICLE_TYPES` does today.

`cycle.run_once()` becomes `run_once(feed_id)`; the crontab entry becomes a
fan-out (`ingest_cycle --all-feeds`, or one entry per feed once there are
enough to want staggering). Keep the per-feed isolation contract that
`device_state`/`ride_watch` already have: one feed's failure must not abort
another feed's cycle.

### 7a. Capabilities must be declared and served

Not every provider supports every feature, and the frontend currently
assumes all of them. Declare per provider, serve at
`GET /api/v1/meta/capabilities?city=&provider=`:

| Capability | Consequence if false |
|---|---|
| `stable_vehicle_id` | no `device_state`, no dwell, no reliability tier, no failed-start detection, no tracked rides, no per-device reports/photos/QR |
| `range_meters` | no quality designation, no range ranks, no battery model |
| `battery_percent` | quality falls back to raw range percentage |
| `deep_link` | no "Unlock in <provider>" button |
| `qr_scan` | no QR bonus flow |
| `known_pricing` | no cost HUD / ride-cost estimate |
| `plate_visible` | rider can't self-identify the vehicle they're standing at |

This table is the honest scope of the project. Don't let the frontend infer
it from whether a field came back null.

### 7b. Denver's other feeds — probed 2026-08-03

Denver has one *operator* but three published GBFS endpoints, and all three
still answer. Probed live:

| Feed | `system_id` | GBFS | State | Vehicles |
|---|---|---|---|---|
| `data.lime.bike/api/partners/v2/gbfs/denver/` | `lime_denver` | 2.2 | **live, `last_updated` ticking, ttl=60** | 3 scooters |
| `gbfs.lyft.com/gbfs/2.3/den/` | `lyft_den` | 2.3 | **frozen at 2024-12-16T17:57Z**, byte-identical across pulls | 2,730 (2,530 scooter + 200 e-bike) |
| `mds.bird.co/gbfs/v2/public/denver/` | `bird-denver` | 2.3 | live endpoint, `last_updated` ticking | **0** |

**Lime is a real, live second Denver provider today.** Three vehicles is a
feature for this work, not a limitation: it is a genuinely different feed
shape at effectively zero ingest cost, which is exactly what phase 2 needs.

**The stable-identity risk is now confirmed, not hypothetical.** Neither
Lime nor Lyft publishes `rental_uris`, so there is no plate and no
`hash_plate()` input:

- **Lime** — `bike_id` is a UUIDv4, no plate. Assume per-trip rotation
  (GBFS 2.2 says it should).
- **Lyft** — `bike_id` is a 32-hex hash that is **not unique within a single
  snapshot**: 2,730 entries, 2,254 distinct ids, one id appearing 15 times
  at different coordinates with different battery levels. It is not a key
  even instantaneously, let alone across cycles.
- **Bird** — no vehicles to inspect; `system_information` advertises only
  app-level `rental_apps` deep links, nothing per-vehicle.

So: **Veo is the only Denver operator that supports per-vehicle identity,
and that is a property of Veo's feed, not of our pipeline.** Plan for it to
stay that way. If per-vehicle intelligence on another operator ever matters,
the route is MDS under a city agreement, not GBFS scraping.

### 7c. The line this draws: fleet analytics vs per-vehicle intelligence

The confirmation above is less damaging than it first looks, because it
splits the codebase along a line that is already almost clean:

**Works on anonymous positions — every provider, no identity needed:**
`compute.py`'s DuckDB spatial join, `snapshot_metadata_core`'s 22 metrics,
`regional_metrics_narrow`, `api_h3` aggregates, `equity-estimate`,
`spatial-snapshot`, `analytics/trend`, and the whole daily SLA / compliance
rollup. **This is the project's origin purpose** — RFP §3.0's "30% of fleet
in equity areas" is a counting exercise over points. It extends to Lime,
Lyft and Bird for free.

**Requires a stable identifier — Veo only:** `device_state`, `device_history`,
dwell, reliability tiers, failed-start detection, `trip_events` and the daily
trip rollups, `ride_watch`/`tracked_rides`, points, QR scans, device photos,
per-device reports, and `battery_model`.

Draw the capability boundary here explicitly rather than per-field. One flag,
`stable_vehicle_id`, gates the entire second list. The capability table in
§7a stays, but this is the one that matters.

### 7d. Concrete adapter findings from the probes

Real divergences the `GbfsAdapter` has to absorb, all observed:

- **`is_disabled`/`is_reserved` are integers in Lyft's feed** (`0`/`1`), bools
  in Lime's and Veo's. `ingest.py`'s
  `if not isinstance(is_disabled, bool): is_disabled = None` silently nulls
  every Lyft flag. Coerce `0`/`1` explicitly.
- **`current_range_meters` is a float in Lyft's feed**
  (`16185.459669359852`), int in Lime's. Today's `int(rng)` handles it.
- **Duplicate `bike_id`s within one payload** (Lyft). `tag_envelope`'s
  signature hash and the `COPY` into `raw_telemetry_points` both tolerate it,
  but anything keyed by device id must not assume uniqueness.
- **`last_reported` per vehicle** — Lime publishes it, Veo does not. A better
  freshness signal than our cycle timestamp where available; add it as an
  optional normalized field.
- **Junk registry metadata is universal.** Lime's `station_information`
  returns a single station named "Denver" at `39.3633,-104.9222` — roughly
  40 km south of the city, near Castle Rock. Same genre as Veo's phantom
  67,000 m `max_range_meters`. Every provider needs a corrections layer;
  `_KNOWN_VEHICLE_TYPES` is not a Veo-specific wart.
- **Coverage is metro, not municipal.** Two of Lime's three vehicles sit
  outside Denver proper (≈Westminster and ≈Wheat Ridge). They fall inside
  the coarse `denver_core` bbox and are correctly demoted by
  `_refine_spatial_status`'s buffered-polygon pass — so the existing
  machinery already handles this, but expect a much higher
  `other_outlier` share for metro-wide operators than Veo produces.

### 7e. Pricing has to move server-side

Veo's Denver rate plans are hardcoded in the *frontend*
(`denver-scooter-fyi/src/config.ts:RATE_PLANS`), and `reported_plan` is a
`resident|visitor|equity` CHECK in `sql/047`. Both are Veo-Denver-specific.
Move to a `provider_rate_plans (feed_id, key, label, unlock_cents,
per_min_cents, …)` table served from `/api/v1/meta/pricing?city=&provider=`,
and relax `reported_plan` from a CHECK to an FK into it. Otherwise every
city fork re-hardcodes pricing and they drift within a month.

## 8. Routing and geocoding: the actual wall

This is where multi-city stops being a software problem.

Today: Valhalla (3.0 GiB cap, Denver-clipped graph) + Photon (2.0 GiB cap,
JVM heap 1536m, Colorado-scoped index). That is ~5 GiB of a 12 GiB VPS whose
declared ceilings already total ~9.6 GiB, for **one** metro.

Options, in order of preference:

1. **One combined graph.** Build the `.pbf` as the union of each served
   metro's extract; make `valhalla.graph_bbox` a list of per-city boxes and
   have `/route/profiles` return the caller's city's box. Valhalla handles
   multi-region graphs fine; memory scales with graph size, so a few metros
   is plausible and statewide is not. Photon likewise: one index scoped to
   the union of the relevant states, with the bbox filter in
   `api_geocode.py` becoming per-city.
2. **Move the sidecars off the box.** A separate routing host that both the
   current and future cities call. Cleanest, costs money.
3. **Per-city sidecar pairs on one box.** Does not fit. Don't.

**Measure before committing.** Build a Denver+one-other-metro `.pbf`, run
it, and look at the actual RSS. The 3 GiB cap was sized for the transient
tile build, so the ceiling is not the steady-state number, but it is the
number that has to fit alongside everything else.

Also note: `refresh_routing_graph` and `refresh_photon_index` are ETag
no-ops most days and log loudly when the artifact changes, because the
container has no Docker socket to restart itself. With more cities feeding
one graph, a change is more frequent — worth automating the recreate before
it becomes a weekly manual chore.

## 8a. Free data from the probes, independent of any of the above

Three things fall out of §7b that are worth having whether or not the
multi-tenancy work ever happens:

- **Lyft's last-known Denver pricing**, from `system_pricing_plans`, frozen
  at shutdown: e-bike `$1.00 unlock + $0.15/min`, scooter
  `$1.00 unlock + $0.41/min`, both `is_taxable: true`. The frontend's
  `COMPARATOR` constant is currently an admitted guess ("Lime's typical
  mid-market US pricing; update … when confirmed"). This is a real, sourced,
  same-city number — and it says Veo's resident rate ($1 + $0.25/min) was
  *cheaper* than Lyft's scooter rate, which is worth knowing before
  publishing a comparator that implies otherwise.
- **119 Lyft dock locations** with `name`, `address` and `capacity` — the
  pre-2025 docked network, still georeferenced.
- **73 live Bird geofencing zones** for Denver, `last_updated` currently
  ticking, with `ride_allowed: false` and a stricter
  `ride_through_allowed: false` subset. Nobody else publishes Denver
  no-ride polygons in machine-readable form. Candidate for a map overlay and
  for Valhalla avoid-polygons in `api_route.py`. Caveat: this is *Bird's*
  encoding of Denver's rules, not the city's own publication — treat it as a
  starting point to verify, not as authority.

The Lyft payload is one frame, not a time series: no trip inference, no
dwell, no history is recoverable from it. Its value is as a golden fixture
at realistic scale (2,730 vehicles, real coordinate distribution, real
malformed edge cases) and as a citable Dec-2024 fleet baseline.

## 9. Cross-cutting decisions

- **Accounts stay global.** One person, one profile, one points ledger,
  across cities. Add `city_id` to `user_points` rows for analytics, not for
  partitioning.
- **Leaderboards go per-city.** H3 r8 cells are geographic so they don't
  collide, but `regional_leaders` and the "area leader" framing should be
  scoped so Denver's volume doesn't bury a smaller city. Add `city_id` and
  filter.
- **CORS.** `allowed_origins` will grow per city. You already have
  `allowed_origin_patterns` — add `^https://[a-z0-9-]+\.scooter\.fyi$` and
  stop enumerating.
- **Magic-link URL.** `accounts.magic_link_url_template` is a single
  `https://denver.scooter.fyi/auth?ml={token}`. With N frontends this must
  be per-request: have the client send its origin, validate it against the
  CORS allowlist (never trust it raw), and build the link from that. Falling
  back to the default sends Boulder's users to Denver's site.
- **Admin panel.** `/admin/cycles`, `/admin/failures`, `/admin/regions` need
  a feed selector, and the cycle list needs the feed name in the table or it
  becomes unreadable at 15 feeds × 720 cycles/day.
- **`GET /` banner and API.md.** Both enumerate every endpoint by hand.
  Budget the doc update — API.md is 3,194 lines and its accuracy is
  load-bearing for the frontend.
- **Rate limits.** Per-IP, no change needed.
- **Privacy policy.** One document today. Per-city data law divergence is a
  real future problem but not a launch blocker; note it and move on.

## 10. Sequencing

The order matters more than the content. **Add a second provider in the
same city before adding a second city** — provider work is pure software at
near-zero infra cost, and it flushes out every hidden Veo assumption while
Denver's boundaries, graph and geocoder stay exactly as they are.

| Phase | Scope | Ships behind | Size |
|---|---|---|---|
| **0** | ~~Verify each candidate provider's feed for a stable id~~ — **done, §7b: none of Lime/Lyft/Bird has one.** Remaining: decide city-in-path vs `?city=` | — | days |
| **1** | `cities`/`providers`/`feeds` tables; `feed_id` on ~30 tables with a `feed_id=1` backfill; `resolve_scope` dependency; `?city=`/`?provider=` defaulting to denver/veo; `denver_core`→`service_area`; timezone from the city row; `_denver`→`_citywide` | nothing user-visible changes | **L** |

| **3** | Frontend de-Denverization (companion doc) — Denver build should be byte-comparable | — | **L** |

Phase 1 is the one to be disciplined about: it must ship with **zero

## 11. Things that will bite

1. **No stable vehicle id outside Veo** (§7b) — confirmed, not a risk any
   more. It doesn't invalidate the plan, it bounds it: other operators get
   fleet analytics (§7c) and nothing per-vehicle. Say so in the UI rather
   than shipping a map where half the popups are empty.
2. **The frontend fetches Veo's GBFS directly** for plate resolution
   (`gbfs.ts`), because Veo's feed is CORS-open. Other providers probably
   aren't. A server-side passthrough would put plates back into *our* API
   and change the privacy posture that `identity.py`'s docstring is built
   around. Decide deliberately; don't let it happen by accident.
3. **The battery model is per-hardware.** Coefficients are fit per vehicle
   model and need ~2 weeks of observations to become trainable. Every new
   provider starts with no battery model and a degraded quality signal.
4. **VPS headroom.** ~9.6 GiB of declared ceilings on a 12 GiB box. City #2
   does not fit without §8.
5. **`_KNOWN_VEHICLE_TYPES` can only be built in the field.** Veo's own
   registry is wrong for two of four live types. Assume every provider's is
   too, and that correcting it requires someone standing next to a scooter.
6. **`tests/fixtures/track-chain-vectors.json`** is a byte-identical
   cross-repo contract with the frontend. Unaffected by any of this — just
   don't touch it.
7. **~1,300 tests, ~95 files.** Phase 1's `feed_id` threading will touch a
   large fraction of them. The `_pg.py` suite is the only real coverage of
   the SQL; run it (`VEO_TEST_PG_DSN=…`, expect 0 skipped) on every
   migration in this plan. Skipped is not passed.
